# Sales service release (Phase 5 Batch 1, Sales half — disabled backend)

2026-11-12 · tracker [#69](https://github.com/kaleemnadeem16/erp/issues/69) · scope [Batch 1 authorisation package](../phases/phase-5-batch1-authorisation-package.md) · direction [ADR 0186](../decisions/0186-deliver-one-progressive-jobs-engine-through-a-bounded-service-pilot.md).
**Inactive.** Both new duties are STAGED and ungranted, the three HTTP endpoints below exist but refuse every caller until the duties are activated and granted (no screen), and a release refuses unless the Jobs module binds a receiver. Nothing here is an
operational delivery by itself; the Jobs receiver ships in the paired half.

## What exists

| Piece | Rule |
|---|---|
| `service_completion_bases` | Append-only, versioned per accepted issued line. Two honest ways to record one (the database guard enforces both): **ISSUED_LINE** — the issued line's description verbatim, citing the acceptance's own consent evidence, no scope stated (the lightweight default); **EVIDENCE_TEXT** — new conditions or an `EXCLUDED`/`REQUIRED` materials/subcontractor scope, only on **dedicated written, authority-verified evidence of the accepting case** that is not the acceptance's own consent evidence, recorded after it, whose factual description *is* the agreed text. One line cannot cite the same evidence twice. Recorder, database-clock time and a predecessor chain that cannot fork. |
| `handover_release_events` | Append-only release evidence. Unique per `(stage, purpose)` (business identity) and per `(actor, request key)` (intent identity). Binds the stage, its baseline and the **head** basis; stores the condition identity/version, cost requirement and status (separate), the cost-policy version and the source generations relied on. Preparation rows are never updated: release status is derived from this row. |
| `RecordServiceCompletionBasis` | Duty `sales.handover.completion-basis.record` (STAGED). Idempotent; a changed text is the next version. |
| `PreviewServiceRelease` / `ReleaseHandoverComponent` | Duty `sales.handover.release` (STAGED). Read-only review returns blockers, cost and applicability status and the fingerprint the release must carry; the release is one transaction (`ReleaseCoordinator`). |
| `ReleasedServiceReceiver`, `JobSalesOrigin` | Sales-owned ports the Jobs module implements/binds. Unbound receiver ⇒ every release refuses (`RELEASE_RECEIVER_UNAVAILABLE`). |
| `SalesJobExecutionContextVerifier` | Implements the Jobs `JobExecutionContextVerifier` for the Sales origin only; takes Sales fences before the Job row is locked; an unsupported origin refuses. Not bound here. |

## Release transaction and lock order

Actor/early duty → (inside the transaction) fresh actor + duty → **authority head → acceptance → case → claim heads (ordered) → quotation revision** (the preparation order, `HandoverAccess::lock`)
→ receipt/replay → business-uniqueness check → basis (must be the head the reviewer saw) → readiness fingerprint → release event row → `ReleasedServiceReceiver::receive` → proof that the
receiver is still in the same connection, backend pid and transaction and durably linked exactly this release to the Job it reported. Any failure rolls back everything. A release only **reads**
the claim heads; it consumes no acceptance claim. `HandoverTransactionContext` reads the connection, transaction level, `pg_backend_pid()` and `txid_current()` from the database; a
caller-supplied boolean or hash proves nothing. `VerifiedServiceRelease` can only be issued by the coordinator.

## Readiness and policy

- Blocking facts reused from preparation: source Item, location, contact, site. The other preparation gaps are answered by: a recorded **completion basis**, the **cost policy**, the **applicability proof** and the **bound receiver**.
- **Cost** (`ReleaseCostPolicy`): cost *required* and cost *status* are separate. The default policy finds no mandatory commercial control, so cost is explicit `UNASSESSED` and does not block. A policy that makes cost mandatory blocks (`SERVICE_COST_EVIDENCE_REQUIRED`) until a supported source supplies evidence; the database also refuses a required cost that is not `EVIDENCED`. Preparation no longer lists `SERVICE_COST_CERTAINTY_UNKNOWN` unless the policy requires cost; the assessment carries a separate `cost` object.
- **Scope classification integrity (review P1, structure authoritative).** The material/subcontractor classification is NOT a flag the operator selects and free text is never read. A **scope declaration** is the WHOLE agreed text and exactly four LF-separated lines — `MATERIALS: <EXCLUDED|REQUIRED|UNSTATED>`, `SUBCONTRACTORS: <EXCLUDED|REQUIRED|UNSTATED>`, `LINE: <issued line id>`, `DELIVERABLE_SHA256: <sha256, lowercase hex, of the issued line's description trimmed of " \t\n\r\v">` — recorded from dedicated customer-agreement evidence whose factual description IS that text. The customer-evidenced record therefore states the scope of THAT exact deliverable text and has no free-text field in which it could be contradicted (the "MATERIALS: EXCLUDED + free text 'Materials required for the work'" case cannot be recorded). A text that starts like a declaration but is not exactly that shape, names another line, or carries another digest is refused as ambiguous; a **conditions-only** text may not contain any keyword line (`MATERIALS:`, `SUBCONTRACTORS:`, `LINE:`, `DELIVERABLE_SHA256:`) anywhere and states no scope (UNSTATED => UNKNOWN => release blocked until a declaration exists). `RecordServiceCompletionBasis` takes no scope parameter: it parses the declaration (`ScopeHeader`, fixed grammar), checks line and digest against the issued line, and **derives** `materials_scope`/`subcontract_scope`; the database guard (`service_completion_basis_scope_declaration`, migration `2026_12_13_500000`, which computes the sha256 itself) refuses the same shapes, so raw SQL cannot bypass the Action. **Head semantics:** the resolver reads the HEAD version of the chain. Re-stating conditions as free text after a declaration makes the head state no scope, so applicability is UNKNOWN and the release refuses (and the preview fingerprint goes stale) until the declaration is recorded again as a new version. The resolver also re-verifies that a stored scope is a declaration for this line whose digest equals the issued description's digest (a legacy-format row from `2026_12_13_400000` counts as UNSTATED) and the proof pins the declared line and digest; start re-verifies both. **Honest limit:** the issued line description is customer-agreed text the system cannot interpret; the declaration binds the scope to its exact digest and nothing more, and independent verification that the evidence is genuine remains the optional company policy of [#114](https://github.com/kaleemnadeem16/erp/issues/114). The ISSUED_LINE path always stays UNSTATED, even if the line description looks like a declaration.
- **No material / no subcontractor** (`SourceApplicabilityProof`, #122, version `SOURCE_APPLICABILITY.2`) — `NOT_APPLICABLE` needs **all three**: (1) the customer-agreed scope itself `EXCLUDED` both materials and subcontractors on an `EVIDENCE_TEXT` basis; (2) **every** source family answers `NOT_APPLICABLE` through the neutral `App\Support\JobSource` contract (`INVENTORY_MATERIAL`, `PURCHASING_SUPPLY`: no supported, validated Job binding exists; generic source provenance is never a Job allocation); (3) the foreign-key catalogue is clean (secondary only). A required scope or a family reporting a supported binding is `APPLICABLE` (blocker `SOURCE_OBLIGATION_UNSUPPORTED`; the first pilot refuses). Anything else — including the **issued-line default basis, which states no scope**, an unregistered family, `SERVICE_ITEM`, an empty query or the absence of foreign keys — is `UNKNOWN` (`SOURCE_APPLICABILITY_UNPROVEN`). So a company that records only the issued-line basis cannot release a pilot service until it records scope evidence. The result is pinned (basis head, scopes, every family status and contract version) in the release's relied-on facts; `SalesJobExecutionContextVerifier` re-proves it for fresh work (start) and refuses when any pinned fact changed. Production registration of the family authorities belongs to the Inventory and Purchasing owners; without it the proof is `UNKNOWN`.

## Fulfilment receipt (Phase 5)

A released service is later fulfilled by its Job's completion: Jobs writes the immutable `handover_fulfilment_receipts` row through `ServiceFulfilmentRecorder` in the same transaction (see
[Job completion and closeout](job-completion-closeout.md#sales-fulfilment-receipt)). It carries the release, the completion event, the agreed-conditions identity and the digest of the exact agreed
deliverable text, and changes no acceptance claim, allocation, capacity or financial record. Closeout refuses a missing or mismatched receipt.

## HTTP surface ([#130](https://github.com/kaleemnadeem16/erp/issues/130))

Thin Sales controller (`HandoverReleaseController`) over the three Actions; every rule stays in the Actions. Each request body names only what the contract allows (unknown fields are a 422); `Idempotency-Key` is required on both writes.

| Endpoint | Duties (Request + Action) | Body | Response (minimal, non-disclosing) |
|---|---|---|---|
| `POST /customer-acceptances/{acceptance}/completion-bases` | `sales.handover.completion-basis.record` + `sales.customer-decision.view` | `agreed_text` (string or null = issued-line default), `evidence_id` | `basis_id`, `version`, `replayed` (201; 200 + `Idempotency-Replayed` on exact replay) |
| `GET /handover-stages/{stage}/release-preview` | `sales.handover.release` + `sales.customer-decision.view` | none | `ready`, `blockers`, `next_actions`, `cost{required,status}`, `applicability{status,materials,subcontract}`, `basis_id`, `basis_version`, `fingerprint` |
| `GET /customer-acceptances/{acceptance}/handover` | `sales.customer-decision.view` + `sales.quotation.view` (the plan-read rules) | none | `acceptance_id`, `prepared`, `plan_id`, `stage_id`, `release_performed` |
| `GET /customer-acceptances/{acceptance}/completion-basis` | `sales.handover.completion-basis.record` **or** `sales.handover.release`, plus the two reads | none | `acceptance_id`, `current` (null or `basis_id`, `version`, `terms_source`, `agreed_text`, `materials_scope`, `subcontract_scope`, `evidence_current`, `recorded_at`) |
| `POST /handover-stages/{stage}/release` | as preview, plus the receiver's independent `job.receive` judged by the Action at the decision point | `basis_id`, `readiness_fingerprint` | `release_event_id`, `job_id`, `job_code`, `replayed` |

Withheld everywhere: evidence and agreed text, source pins/versions, family answers, lineage references, cost policy version, full Job records. Unknown or foreign stages/acceptances are 404 after the duty check; a stale review, reused key or already-released stage is 409 (`PREVIEW_TOKEN_STALE`, `REQUEST_KEY_REUSED`, `RELEASE_ALREADY_RECORDED`); a blocked or unevidenced release is 422. A fresh key for the same business intent resolves to the one existing release and Job (the Action reports `replayed:false`; no row is added). The HTTP layer's global string trimming means a whitespace-only `agreed_text` becomes null/empty before the Action sees it. Tests: `HandoverReleaseApiTest` (real HTTP over the real Jobs receiver), plus the existing race/COMMIT proofs.

## Screen ([#130](https://github.com/kaleemnadeem16/erp/issues/130) follow-up)

`/handover-plans/:plan` (feature `handover-release`, behind the same production gate as the quotation and acceptance screens; exact duties on the page and again on the server) shows the prepared handover and the issued description, records completion conditions by **citing existing customer evidence** (the issued description on the acceptance's own message, or a later written, authority-verified message whose exact text is sent; never typed text, never a checkbox or local scope declaration), reviews release readiness (the server's blockers and next actions, unknown codes fall back to a neutral line) and enables **Release to a Job** only when the review says ready, behind one confirmation. The result shows the Job number and links to `/jobs/{id}`; an already-released stage says a second Job is impossible. Business rules stay in the Actions.

Those gaps are now closed (follow-up): `GET /customer-acceptances/{acceptance}/handover` (acceptance view + quotation view, the plan-read rules; no new duty) answers `prepared`, `plan_id`, `stage_id` and `release_performed` for ONE acceptance — not a directory — and the acceptance screen links to the prepared handover from it. `GET /handover-plans/{plan}` now derives `release_performed` and `release` from the immutable `handover_release_events` row (`state` stays `PREPARED`: preparation rows are never rewritten); the Job reference (`id`, `code`) is included only for a person who currently holds `job.view` (`job_access` = `VISIBLE`, `NOT_PERMITTED` or `UNAVAILABLE`). `GET /customer-acceptances/{acceptance}/completion-basis` shows the CURRENT (head) conditions — version, exact agreed text, source, scope, `evidence_current`, recorded time — to a person holding the record **or** the release duty (plus the two reads); no other versions, no evidence id, no pins, no money. The screen reopens a released plan as *Already released — existing Job* (never "a Job was created"), asks the server for the release status immediately before sending a release, and refreshes the review whenever the head conditions differ from the reviewed ones.

## Corrected customer evidence (decision recorded with #130 follow-up)

Observations are append-only; a correction is a later observation naming its predecessor, so an observation that has a successor is *superseded*. Policy applied (the smallest rule the existing owning source supports, no new customer-agreement rules):

- **Recording.** `RecordServiceCompletionBasis` refuses to cite a superseded observation as NEW agreement evidence (`INVALID_INPUT` on `evidence_id`); the case is locked, so a correction cannot slip in between the check and the insert. The unique-evidence-per-line rule still prevents re-using an old observation.
- **Release.** A head basis (`EVIDENCE_TEXT`) whose evidence has since been corrected no longer states what the customer currently says: the review reports the blocker `COMPLETION_EVIDENCE_SUPERSEDED` (so the fingerprint moves and an earlier review is stale, 409 `PREVIEW_TOKEN_STALE`) until a new basis version cites the current observation. The release itself re-assesses it under the same locks, so a correction between review and release also refuses (422 `HANDOVER_NOT_READY`/409 stale).
- **History.** Nothing is rewritten. An existing release is answered (business replay) before readiness is evaluated and the Job baseline already carries the agreed text it was released under, so a legitimate historical release and its Job are unchanged by a later correction. `AppendCustomerDecisionEvidence`, the case lock order and the preparation/release lock order are unchanged.
- **After the release (Jobs execution).** `SalesJobExecutionContextVerifier` reports `commandReady = false` once the head basis's agreement evidence is superseded, judged under the source locks it already takes (authority head, acceptance, case, claim heads). So START and COMPLETE refuse (`NOT_READY_TO_START` / `NOT_READY_TO_COMPLETE`) and the closeout assessment blocks with `SOURCE_NOT_READY`. `recordEligible` is unchanged: the Job stays readable, can take holds, and an authorised exact retry of an already-recorded command still answers. Nothing is reopened or cancelled, and the baseline, completion and release rows are never rewritten. Recovery, or a new basis on the current observation, is separately governed and not automated here. A correction that commits after the verifier's locks are taken is serialised after that command, as with any concurrent source change.
- **Open decision (not invented).** The acceptance's OWN consent evidence (the ISSUED_LINE default path) is the acceptance's fact, not new agreement; a later correction of it is a question for the Customer Decision owner (R7 correction of accepted business) and is deliberately not treated as invalidating the acceptance or its default basis here.

## Limits (deliberate)

No screen, completion, closeout, cancellation or recovery. The mandatory-cost policy has no delivered source of cost evidence, so a *required* cost always blocks; only the default (not required) path can release. Existing acceptances have no completion basis until an authorised actor records one.
