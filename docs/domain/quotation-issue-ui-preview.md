# Quotation issue-readiness and approval presentation preview

These are disabled, unregistered, fixture-only presentation components for Batch B. They are not routed or linked in the application and make no API calls. `QuotationReadinessScreen` requires the off-by-default gate and `sales.quotation.prepare`; `QuotationApprovalScreen` requires that same gate and the separate `sales.quotation.issue` duty. The latter remains STAGED. Fixture-only renderers cannot be taken as a permission grant.

The safe assessment shape comes from Agent A's **internal** `AssessQuotationIssueReadiness` Action on `phase4/ql3-issue-quotation` at `0c9a774a`: `revision_id`, `input_generation`, `issue_ready`, and blockers with `code`, `scope`, and nullable `line_id`. This is not a published HTTP Resource or generated client. The preview checks consistency, discards extras, and presents recognised blockers as human text; unknown codes remain blockers with generic text and are never printed raw. Evidence, costs, tax rates, fingerprints and arbitrary server messages are not rendered. A pass describes only that assessment, not current authority or issue success. The approval preview has no active approval, issue or acceptance command.

The draft G-A1/G-A2 proposal on #57 remains subject to separate owner decisions and authorisation. It proposes an internal IssueQuotation Action rechecking current authority, generation and evidence under locks and recording a frozen issued revision; no HTTP adapter or UI contract exists yet. It also proposes customer decision intake and ordinary full acceptance, not a generic approval state machine. Reconcile both screens with the final approved API, capability checks, policy/record access and exact reviewed generation before any wiring or activation. Never infer a zero tax, a passing control, an approval, an issued number or an acceptance. Unknown and unevaluable remain blockers. Current default providers deliberately report tax and controls as unconfigured.

Build the frontend first, then run `docker/frontend/run-e2e.sh quotation-issue-preview.unit.spec.ts --project=unit`. These isolated fixtures use synthetic data and intercepted requests. Tests cover malformed/inconsistent assessments, stripping private extras, both default-deny gates, unknown blockers, disabled issue control, keyboard focus, phone-width overflow and serious/critical accessibility checks. They do not test an actual backend endpoint or authorise issue.
