# R9 — Registration, grants, migration and staging contract

**2026-10-15 · ACCEPTED0138 / SPECIFIED. No live registrations/grants or rollout authorised.**
The [duty matrix](../domain/sales-duty-matrix.md) classifies exact names/operations/fields/holders.
Real grant decisions require implementation rollout manifest and owner-reviewed holder inventory.
Role presets, if later delivered, are transparent named collections of explicit rights, no authority
engine, wildcard or role-name check. Research does not select real principals.

## Required implementation manifest — reviewable before activation

Per capability and company record: module owner, exact string and enforcement points; ACTIVE for
supported delivery versus RESERVED/DORMANT with no entry point; equivalent predecessor evidence or
NONE; role/direct holder identities; effective scope before/after; minimum projection/sensitive file
profile; automatic-growth exclusion and applicable verified mandate/reference; approved limit/approval
configuration; activation prerequisites; migration/backout/staging evidence and responsible code owner.
Include HTTP/console/import/background/bootstrap/demo/all-vocabulary helpers and attachment/report
surfaces. Exact strings must match current registry/code and accepted PR/FR/QL/CA/HA/DOC/DF contracts;
conflict blocks affected operation, never silently aliases or broadens a gate.

## Safe implementation order

1. Read-only inventory current companies/roles/direct grants/memberships/mandates/effective RecordScope,
   actual old operations and helper behaviour. No production secrets/permission changes in planning.
2. Reconcile names/owners: existing eight CRM unchanged; ordinary submit uses quotation.prepare;
   shared review registry accepts Sales-specific technical permission instead of double PO+Sales
   gate; Company brand reuses profile; one tax registration path, existing source/currency/approval
   reads retained. No generic download/duplicate Sales template permission.
3. Register only slice-needed names through owning provider, with S exclusions in same delivery as
   any all-vocabulary consumer. Dormant future exception/departure/claim-release unsupported paths
   stay unregistered or explicitly reserved with proof of no reachable writer; no automatic enablement.
4. Apply owner-reviewed explicit N/S holder recipe only when authorised. New feature has no inferred
   CRM incumbent. For actual predecessor continuity preserve exact company/role/direct origin and
   scope; no unrestricted direct copy of a limited role. No broad role granted to satisfy a test.
5. Re-sync honours exclusions, preserves legitimate explicit excluded grants and verifies qualifying
   full-access mandate role/company/member/effective approval evidence. Missing proof excludes.
   Future scope checks must preserve restriction; existing FullAccessMandates::covers alone is not
   proof new scope-safe rollout exists. If an automatic helper would broaden new rights before
   owner-reviewed recipe, keep new capabilities excluded/feature disabled until manifest reconciles it.
6. Guard Request+Action, protect projections/queries/worker/context, register routes/reads/ratchets,
   deploy client/UI/demos and migrations together, then verify staging with authorised identities.
   Public activation follows owner sign-off/rollout authority, not architectural acceptance.

## Migration and backout

Use additive module-owned registration/grant migrations; idempotent per-company changes and auditable
mapping old→new provenance. Ledger migration-introduced grant IDs/origin/scope/approval reference so
backout can distinguish pre-existing/independently assigned rights. Re-run must no-op without clearing
explicit access or credential lifecycle. No permission-count/all-rights-today or role-name inference.

Backout disables new entry points/workers first, retains business/audit/receipt history. Revoke only
proven migration-introduced grants that have not been independently reassigned/changed; uncertain
mapping is reviewed, never blanket revoked. Keep registered capabilities still referenced by code,
role/mandate/evidence or an active writer. Do not delete permission rows under running checks, cascade
issued evidence or remove parent scope limits to make rollback succeed. Destructive down after actual
usage must refuse safely or require separately approved backout plan. Isolated apply/rollback/reapply
proves both fresh and upgrade paths with existing company-specific grants.

## Staging verification and owner inventory

| Check | Required evidence, no assumed pass |
|---|---|
| Incumbent continuity | Each unchanged CRM holder/duty and source read behaves as before; no CRM→new authority expansion |
| Negative holder | Ordinary editor/manager/admin name gets no new sensitive right without approved assignment/mandate |
| Mandate | Correct company/role/member/effective approval qualifies only approved scope; foreign/future/missing/mismatched evidence excludes |
| Per-duty scope | Unrelated all-scope grant does not widen restricted sensitive duty; company-wide grant explicit; unsupported limited mode403 |
| Projection | No-capability/direct Action/HTTP/worker denials; cost-blind safe outcome; approval reasons/limits; full PDF versus quantity-only and confidential attachment |
| No side doors | Search/count/filter/sort/include/history/export/download/cache/provider/import/console all equivalent guarded profiles |
| Idempotence/backout | Second migration/sync no added escalation; legitimate explicit excluded rights preserved; rollback removes only owned additions |
| Live-holder inventory | Owner reviews actual principals/company/role/direct/effective scopes, enabled capability/approval limit and deployment sign-off; real assignment outside planning |

Staging verification owner is implementation/deployment coordinator and human owner, not planning.
Do not run application audits/tests, alter passwords, seed production or assign live holders here.
If staging unavailable, delivery remains not verified/publicly disabled with concrete cause/owner.
No automatic completion based on a green mock or docs link check. Each public route's activation
record ties implementation commit, migration/grants, checks/date and authorised release decision.
